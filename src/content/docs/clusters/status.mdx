## Check running workloads

```bash
sparkrun cluster status
sparkrun status              # alias
```

This shows workloads reported by enabled executors on your cluster hosts, grouped by job.

## Output

The status command displays:

- **Running jobs** — containers grouped by workload ID with role (head/worker/solo), host, status, and container image
- **IP mapping** — when InfiniBand was detected during launch, shows the complementary IP alongside each host (e.g. management IP if you defined the cluster by IB IPs, or vice versa)
- **Idle hosts** — hosts that have no sparkrun containers running
- **Pending operations** — downloads or image distributions currently in progress that haven't launched containers yet, with elapsed time and a note that they will consume VRAM once launched
- **Copy-paste commands** — ready-to-use `sparkrun logs` and `sparkrun stop` commands for each running job

:::tip
The status output includes copy-paste-ready `logs` and `stop` commands for each running job.
:::

:::note
Pending operations are tracked through shared reservations. If a `sparkrun run` process is downloading a model or distributing a container image, it will appear in the pending operations section even though no container is running yet. This helps you account for upcoming VRAM usage when planning additional workloads.
:::

## Options

```bash
# Check a specific cluster
sparkrun cluster status --cluster mylab

# Check a saved subgroup
sparkrun cluster status --cluster pair-a
```

If no options are given, uses the default cluster.

## Interactive monitoring and logs

Run `sparkrun cluster monitor --cluster mylab` for live host metrics and workload
occupancy. Select a host for sensor sparklines, including network rates, or select
a workload to view logs, search them, or export retained history. See
[host metrics and monitor controls](/cli/cluster-commands/#host-metrics-and-history).

## Placement, state, and cache policy

Hardware inventory, per-host executor destinations, and live reservations determine
placement. Ordinary workloads reserve accelerators exclusively; a low engine memory
fraction does not automatically permit co-location. See [Schedulers](/advanced/schedulers/).
Workload metadata is shared across direct and daemon calls, while daemon operation
history is separate. Missing observations are not proof of idle capacity.
Cluster model validation/selection/provider settings and runtime cache cleanup are
covered in [Model Cache Management](/advanced/cache-management/).
