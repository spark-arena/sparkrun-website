[vLLM](https://github.com/vllm-project/vllm) is the default runtime in sparkrun.
For recipes, **use `runtime: vllm`** and select the backend with
`defaults.distributed_executor_backend`:

- **`mp` (default)** — native distributed/multiprocessing, resolved as `vllm-distributed`.
- **`ray`** — Ray head/worker orchestration, resolved as `vllm-ray`.

Omit the backend setting to use distributed/mp. Keep `runtime: vllm` when
switching between backends; see [Runtime alias resolution](#runtime-alias-resolution).

## Features

- Solo and multi-node tensor parallelism across DGX Spark nodes
- Broad model support (most HuggingFace models)
- PagedAttention for efficient KV cache management
- Tool calling support
- Two multi-node strategies: vLLM native distributed or Ray clustering

## Container images

Both `vllm-distributed` and `vllm-ray` use the same container images. sparkrun works with ready-built images including:

- Spark Arena Official Images (built from @eugr's repo): `ghcr.io/spark-arena/dgx-vllm-eugr-nightly:latest` and `ghcr.io/spark-arena/dgx-vllm-eugr-nightly-tf5:latest`
- [Self-built community images from eugr/spark-vllm-docker](https://github.com/eugr/spark-vllm-docker) (often the first to have the latest fixes)
- [Official NVIDIA Images](https://catalog.ngc.nvidia.com/orgs/nvidia/containers/vllm)

We recommend that you use the Spark Arena images for sparkrun recipes; when you use the official Spark Arena images, sparkrun will automatically manage using the latest eugr/spark-vllm-docker.

### Sentinel images

The Spark Arena nightly image names — `ghcr.io/spark-arena/dgx-vllm-eugr-nightly:latest`, its `-tf5` variant, and the Docker Hub `eugr/spark-vllm` image — are **sentinel images**. When you reference one at `:latest`, sparkrun's `eugr` builder resolves it to the authoritative published nightly and **pulls** it.

This is the **default for all official v2 recipes**: it gives you a stable, single name to reference while sparkrun handles versioning. The `-tf5` and non-tf5 nightlies are identical now, so both resolve the same way.

:::note[Changed in July 2026]
Upstream eugr moved to publishing stable container images rather than expecting
local builds, and sparkrun followed. Referencing a sentinel at `:latest` used
to trigger a **rebuild from the upstream repo** before each launch; it now
pulls a prebuilt image.

To build locally from upstream wheels instead, opt in explicitly with
`build_args: ["--use-wheels"]` in the recipe.
:::

To pin a specific image rather than tracking the nightly, use any non-`:latest` tag (e.g. `ghcr.io/spark-arena/dgx-vllm-eugr-nightly:2026-03-01`) — sparkrun uses that tag as-is. Tags can be moved upstream; use a digest when content identity must be immutable.

See [Phase 2: Building image](/developer-reference/execution-flow/#phase-2-building-image) for the full builder lifecycle.

## Speculative decoding

When `defaults.speculative_config` has a `model` field, sparkrun pre-syncs that
draft model to all target hosts alongside the primary model. Both YAML mappings
and JSON-object strings are supported, including mappings imported from the lil
catalog. This happens during the
[distribution phase](/developer-reference/execution-flow/#phase-3-distributing-resources)
so the container can use the cached drafter under sparkrun's offline-hub default.

```yaml
defaults:
  speculative_config:
    method: dflash
    model: z-lab/Qwen3.6-35B-A3B-DFlash
    num_speculative_tokens: 5
```

Both `vllm-distributed` and `vllm-ray` honor this. Sparkrun passes the full mapping
as one JSON argument to `--speculative-config` and uses `model` plus the optional
`revision` for draft preparation. The draft does not inherit the primary model's
`model_revision`, since it belongs to a different repository.

Use `-o speculative_config.model=org/other-drafter` to change the model prepared
for that launch, or `-o speculative_config.num_speculative_tokens=3` to tune one
field while preserving the rest. If the original config pins a draft revision,
update that field too when changing repositories. See
[mapping overrides](/recipes/format/#override-one-field-of-a-mapping).

## Runtime alias resolution

We recommend `runtime: vllm` for both variants. For recipes that let Sparkrun
generate the command, select the backend in `defaults`:

| `defaults.distributed_executor_backend` | Resolved runtime | Orchestration |
| --- | --- | --- |
| Omitted | `vllm-distributed` | Native distributed/mp (default) |
| `mp` | `vllm-distributed` | Native distributed/mp, selected explicitly |
| `ray` | `vllm-ray` | Ray head/worker cluster |

To select native distributed/mp explicitly:

```yaml
runtime: vllm
defaults:
  distributed_executor_backend: mp
```

For Ray, change only the default:

```yaml
runtime: vllm
defaults:
  distributed_executor_backend: ray
```

For one launch, override that setting without editing the recipe:

```bash
sparkrun run my-vllm-recipe -o distributed_executor_backend=ray
sparkrun run my-vllm-recipe -o distributed_executor_backend=mp
```

The concrete names `vllm-distributed` and `vllm-ray` remain supported, but prefer
the `vllm` alias so the backend setting controls selection. Older command
templates containing `--distributed-executor-backend ray` can also select Ray;
an explicit `-o distributed_executor_backend=mp` overrides that hint.

## Example recipe

This recipe uses `runtime: vllm`, which resolves to `vllm-distributed` by default:

```yaml
model: Qwen/Qwen3-1.7B
runtime: vllm
container: ghcr.io/spark-arena/dgx-vllm-eugr-nightly:latest

defaults:
  port: 8000
  host: 0.0.0.0
  tensor_parallel: 1
  gpu_memory_utilization: 0.8
  max_model_len: 32768
  enable_prefix_caching: true
```

## Configuration options

Use `runtime` and `defaults` and omit `command` for the supported settings
below. Add a command only when you need an unusual engine flag that sparkrun
does not map. These are the flags generated by sparkrun; the selected engine
image must also support them.

Set values under `defaults`, for example `port: 8000`, or override them with
`-o port=9000`. Unset values are omitted unless a runtime/platform default
supplies them. Boolean toggles emit a bare flag when true and omit it when false,
except where the table lists an explicit negative or valued form. Mapping/list
values are rendered as one JSON argument for flags that accept JSON. Unknown
keys do not automatically become engine flags.

The generated command is `vllm serve MODEL`. Set `model` and `model_revision`
at the recipe's top level; model preparation and revision arguments are managed
by sparkrun. Both vLLM variants share these mappings, with different parallelism
constraints described below.

## Multi-node with vllm-distributed (default)

With `runtime: vllm` and the backend omitted or set to `mp`, Sparkrun selects
`vllm-distributed`. It uses vLLM's built-in multi-node support, with Sparkrun
handling container lifecycle, InfiniBand detection, and node coordination:

```bash
sparkrun run qwen3-1.7b-vllm --tp 2
```

This explicitly requests tensor parallelism across two DGX Sparks in the selected cluster.

No Ray cluster is involved — vLLM coordinates the nodes directly via its native distributed backend. See [Execution Flow](/developer-reference/execution-flow/) for the full multi-node orchestration details.

### Tensor, pipeline, and data parallelism

`vllm-distributed` supports three parallelism regimes on DGX Spark (one GPU per node, so each parallel dimension consumes physical hosts):

| Mode | Defaults | Behavior |
|---|---|---|
| Cross-node TP/PP, single replica | `tensor_parallel: N` or `pipeline_parallel: N` (DP=1) | sparkrun appends `--nnodes`, `--node-rank`, `--master-addr`, `--master-port`; worker ranks get `--headless`. |
| Pure data parallelism | `data_parallel: N` (TP=PP=1) | Each node is its own replica; sparkrun appends `--data-parallel-size`, `--data-parallel-rank`, `--data-parallel-address`, `--data-parallel-rpc-port`. |
| Hybrid (TP/PP × DP) | `tensor_parallel: T, data_parallel: D` | sparkrun maps replicas to host groups of size `T·PP`; `--master-addr` is the first host of each replica; both flag sets are emitted. |

Required node count = `tensor_parallel × pipeline_parallel × data_parallel`. The `data_parallel_rpc_port` defaults to `13345` and can be overridden in recipe defaults.

:::caution[vllm-ray and data parallelism]
The Ray backend currently does **not** support `data_parallel > 1`. For DP
workloads, keep `runtime: vllm` and use `defaults.distributed_executor_backend: mp`
or omit the backend setting. The Ray runtime rejects DP > 1 during validation.
:::

## Multi-node with vllm-ray

`vllm-ray` forms a Ray cluster first, then runs the serve command on the head node. sparkrun handles Ray cluster setup, InfiniBand detection, and container lifecycle automatically.

Select Ray through defaults while keeping the recommended runtime name:

```yaml
runtime: vllm
defaults:
  distributed_executor_backend: ray
```

### Ray-specific options

These options apply only to `vllm-ray`:

| Option | Default | Description |
|---|---|---|
| `--ray-port` | 46379 | Ray GCS port |
| `--dashboard` | off | Enable Ray dashboard |
| `--dashboard-port` | 8265 | Ray dashboard port |

## Choosing between variants

Both variants support the same models and vLLM flags. The difference is in multi-node orchestration:

- **Distributed/mp (default)** uses vLLM's built-in coordination without Ray.
  Use `runtime: vllm` and omit `distributed_executor_backend`, or set it to `mp`.
- **Ray** provides Ray's cluster management, dashboard, and monitoring. Keep
  `runtime: vllm` and set `defaults.distributed_executor_backend: ray` when you
  need those features.

For single-node (solo) workloads, both variants behave identically.

## Startup and cache policy

Default `run` follows startup logs until readiness and required hooks complete.
vLLM declares streaming Chat Completions, Responses, and Messages probes plus a
`/health` endpoint. Which observations run depends on executor support; missing
observers do not produce inferred timing values. See [run](/cli/run/).

On DGX Spark, sparkrun supplies `gpu_memory_utilization: 0.80` only when the
recipe and overrides leave it unset. This serving setting is separate from the
[scheduler’s 0.90 cap](/advanced/schedulers/). Runtime compilation caches are
separate from model files; see [Model Cache Management](/advanced/cache-management/).
