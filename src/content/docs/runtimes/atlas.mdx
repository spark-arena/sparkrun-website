[Atlas](https://atlasinference.dev/) is a pure-Rust LLM inference server with a native NCCL-based distribution layer. sparkrun's `atlas` runtime launches `spark serve` and orchestrates the container lifecycle, NCCL bootstrap, and OpenAI-compatible HTTP endpoint.

## Features

- Pure-Rust inference server with low overhead
- Native NCCL bootstrap via `--rank`, `--world-size`, `--master-addr`, and `--master-port`
- Tensor parallelism (`--tp-size`) and expert parallelism (`--ep-size`) — both can share the same physical ranks (overlapping groups) or form an orthogonal mesh
- Optional speculative decoding (`--speculative`, `--ngram-speculative`, `--self-speculative`), DFlash attention, and prefix caching
- `--high-speed-swap` path that uses `io_uring` for fast KV/cache spill, supported by sparkrun's [shared Docker seccomp profile](/advanced/executors/#seccomp-profiles)

Atlas derives its world size from the two parallelism dimensions, so you set
`tensor_parallel` and `ep_size` and sparkrun maps the resulting ranks onto
physical hosts:

- `world_size == tensor_parallel × ep_size` — orthogonal mesh
- `world_size == tensor_parallel == ep_size` — overlapping groups

Atlas requires a GB10 host: the runtime declares a `gb10` capability
requirement, and a launch placed on a host without it fails the compatibility
check before any side effects.

## Official recipe registry

The Atlas maintainers publish an official sparkrun recipe registry at [Atlas-Inf/sparkrun-recipes](https://github.com/Atlas-Inf/sparkrun-recipes). Treat this as the **authoritative source for official Atlas recipes** — recipe formats, supported flags, and container tags there are kept in sync with upstream Atlas releases.

The `@atlas` registry is bundled as a default registry in sparkrun **v0.2.31 and later**, so it's discoverable out of the box without manual `sparkrun registry add`:

```bash
# List recipes from the official Atlas registry
sparkrun recipe list --registry atlas

# Run a recipe from the @atlas registry
sparkrun run @atlas/<recipe-name>
```

If you're on an older sparkrun release, you'll need to update to use the atlas runtime and registry.

## Running

```bash
sparkrun run @atlas/qwen3.5-35b-a3b-nvfp4
```

## Container images

Default image prefix: `azeezish/atlas-gb10`

```yaml
container: azeezish/atlas-gb10:latest
```

See the [Atlas GitHub repository](https://github.com/Atlas-Inf/atlas) for image tags and release notes.

## Example recipe

This single-node example illustrates Atlas settings. Inspect the current `@atlas` recipe before choosing an image tag or model configuration:

```yaml
recipe_version: "2"
model: Sehyo/Qwen3.5-35B-A3B-NVFP4
runtime: atlas
container: azeezish/atlas-gb10:latest
max_nodes: 1

metadata:
  description: |
    Example Qwen3.5-35B (A3B MoE) NVFP4 + MTP configuration on one GB10.
  category: agent
  model_params: 35B
  model_dtype: nvfp4
  quantization: nvfp4
  kv_dtype: nvfp4

defaults:
  port: 8888
  host: 0.0.0.0
  max_model_len: 8192
  kv_cache_dtype: nvfp4
  gpu_memory_utilization: 0.88
  scheduling_policy: slai
  speculative: true
  mtp_quantization: nvfp4
  enable_prefix_caching: true
```

When no `command` template is provided, sparkrun generates `spark serve {model}` with flags derived from `defaults` via the Atlas flag map.

## Speculative decoding

When a recipe sets `draft_model` in `defaults`, sparkrun automatically pre-syncs that model to all target hosts alongside the primary model — the same way it pre-syncs draft models for vLLM and SGLang speculative recipes. This happens during the [distribution phase](/developer-reference/execution-flow/#phase-3-distributing-resources) so the container never has to fetch the draft from HuggingFace at launch time (which would fail under sparkrun's offline-hub default).

```yaml
defaults:
  speculative: true
  draft_model: avarok/qwen3.5-35b-a3b-nvfp4-draft
  num_drafts: 2
```

This works with any of the speculative modes (`speculative`, `self_speculative`, `ngram_speculative`, `dflash`); the only requirement is that the draft model name is set in `defaults.draft_model`.

## Parallelism model

Atlas derives `world_size` from `tensor_parallel` and `ep_size`:

- `world_size == tp_size * ep_size` — orthogonal mesh (TP and EP on independent ranks)
- `world_size == tp_size == ep_size` — overlapping groups (both groups share the same physical ranks)

sparkrun maps the resulting world size to physical hosts automatically and launches the ranks through the native NCCL path. The earlier single-node restriction is removed in the pinned 0.4.0 source. For a single-node recipe, set `tensor_parallel: 1` and omit `ep_size` (or set it to `1`).

## Docker options

Atlas uses the [shared Docker seccomp profile](/advanced/executors/#seccomp-profiles),
which permits `io_uring_setup`, `io_uring_enter`, and `io_uring_register` while
retaining the rest of the bundled Moby policy. The Atlas runtime does not add
`seccomp=unconfined`; disabling seccomp is an explicit executor configuration choice.

The Atlas runtime adds these capabilities on every Docker launch, including when
`high_speed_swap` is disabled:

| Option | Capability |
| --- | --- |
| `--cap-add=IPC_LOCK` | Permits locking memory, used by pinned-memory and RDMA paths |
| `--cap-add=SYS_NICE` | Permits elevated scheduling and priority operations |

These are Atlas additions. The shared Docker settings supply unlimited locked
memory with `--ulimit memlock=-1:-1` for normal non-privileged launches; that limit
is separate from the `IPC_LOCK` capability. See
[Capabilities and locked memory](/advanced/executors/#capabilities-and-locked-memory).

`SYS_NICE` describes the current launch configuration, not a universal requirement
for high-speed swap: Linux 5.13 and later allow SQPOLL without special privileges.
See the [Linux io_uring documentation](https://man7.org/linux/man-pages/man2/io_uring_setup.2.html).

## Startup and cache policy

Atlas does not declare streaming inference readiness observers. Default `run`
uses supported endpoint checks and waits for required hooks; it does not report
unavailable first-token timings. See [run](/cli/run/).

The example’s memory utilization is an explicit recipe setting, separate from
[scheduling reservations](/advanced/schedulers/). Model files, draft models, and
runtime caches have different validation and cleanup needs; see
[Model Cache Management](/advanced/cache-management/).
